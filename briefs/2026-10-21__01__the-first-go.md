# Naming decisions: AWS twin, twins hub, providers family

Captured: 2026-10-21
Context: naming for the site proposed in
https://newsroom.sgit.ai/articles/aws-from-the-vault.html

---

## 1. Decision: the AWS site is `aws.twin.sgit.ai`

- **Domain:** `aws.twin.sgit.ai`
- **Repo:** `SGit-AI__Website__Twin__AWS` (follows `SGit-AI__Website__Hook__Tokens`)
- **Hub:** `twins.sgit.ai`

### Why a twin, and not a console

The site is designed twin-first:

1. Build the twin: an AWS-shaped interface (S3, Lambda, EC2, IAM, billing,
   logs) whose backend is a vault.
2. Put the real connection in front of it as a second backend behind the
   same interface: a temporary IAM Identity Center session pasted into the
   user's vault.
3. Everything built against the twin works against the live account,
   because consuming code is written against the interface, not the backend.

This is the same pattern as the one working twin today, the S3-compatible
vault container: boto3 cannot tell the difference, the backend is swappable
(real S3, vault, memory), and the consuming code does not change.
`aws.twin` is the second instance of that pattern, not an exception to it.

### What this gives the workflow

- Develop and test every interface against the vault, with no credentials.
- Rehearse multi-account, multi-region deploys (first job: SG/Send server
  components) against the twin before running them live.
- Snapshots are vault commits either way, so "what changed between Monday
  and Friday" works the same for live-sourced and hand-seeded data.
- Account graph: resources as nodes, relationships (role → policies,
  function → bucket, instance → security group) as edges.

### Options considered and rejected

| Option                 | Why not                                                                 |
|------------------------|-------------------------------------------------------------------------|
| `aws.sgit.ai`          | Loses the twin-first framing, which is the core of the design            |
| `aws.platform.sgit.ai` | "Platform" names nothing in the estate; a namespace with one occupant   |
| `aws.provider.sgit.ai` | Provider sites are reports, not tools (see section 5 for a companion)   |

## 2. Naming convention (by design)

- **Plural = the hub / the family:** `twins.sgit.ai`, `hooks.sgit.ai`,
  `providers.sgit.ai`
- **Singular = one instance, at that moment in time:**
  `aws.twin.sgit.ai`, `tokens.hook.sgit.ai`, `elevenlabs.provider.sgit.ai`
- **Repos:** `SGit-AI__Website__<Family>__<Instance>`, singular family name
  (e.g. `Hook__Tokens`, `Provider__ElevenLabs`, `Twin__AWS`)

Ops note: each singular namespace needs its own wildcard cert
(`*.twin.sgit.ai`, `*.hook.sgit.ai`, `*.provider.sgit.ai`), since
`*.sgit.ai` does not cover second-level subdomains.

## 3. TODO: update the naming ruling on twins.sgit.ai

Page: https://twins.sgit.ai/naming/index.html

The current ruling says a twin "holds no credentials", and that the S3
container blurs the line by also holding backend access. Add a paragraph
that resolves this:

> A twin's interface never holds credentials. A twin can have a live
> backend; when it does, the credential belongs to that backend, not to
> the twin, and lives in the user's vault for the lifetime of the session
> (for AWS: a temporary IAM Identity Center session, 1–12 hours, 1 hour
> by default). The S3 container and the AWS twin are the two worked
> examples of this: interface first, backends swappable, live access as
> one backend among several.

Also:

- [ ] Keep the execution broker distinct: the broker is a standing,
      credential-holding intermediary; a twin with a live backend borrows a
      user-held, time-bounded session.
- [ ] Name-watch: add any capitalised form used (e.g. "AWS Twin") to the
      allow-list in `admin/build/validate.js` with its meaning, or use
      lower case ("the AWS twin") throughout.
